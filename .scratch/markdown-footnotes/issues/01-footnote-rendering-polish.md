# 01: Footnote rendering polish

**What to build:** GFM footnotes (`[^1]`, `[^note]:`) already render — Astro's default `unified` pipeline emits `<sup><a data-footnote-ref>` refs and a trailing `<section data-footnotes class="footnotes">` with backrefs. No plugin or config change is needed to turn them on. This ticket covers the three rough edges that make them look broken:

1. **The hidden footnote heading is visible.** The generated section starts with `<h2 class="sr-only" id="footnote-label">Footnotes</h2>`, but no `sr-only` utility class exists in `src/styles/global.css`, so the heading renders on the page — and `rehypeAutolinkHeadings` appends a `#` anchor to it, so a stray "Footnotes#" line appears above the list.
2. **The footnote heading pollutes the table of contents.** `src/components/TableOfContents.astro` collects every heading in the post body, so any post with footnotes gets a bogus "Footnotes" TOC entry even once the heading is visually hidden.
3. **Footnotes are unstyled.** There are no `.footnotes` rules; the list inherits body type, with no separator rule, no smaller size, and no backref affordance styling.

**Out of scope (raise separately if wanted):** whether footnote text should be excluded from `search-index.json` and `feed.xml`.

## Agent Brief

**Category:** bug
**Summary:** GFM footnotes render a visible "Footnotes#" heading, a bogus TOC entry, and no styling — fix all three.

**Current behavior:**
GFM footnotes render via the default markdown pipeline; no plugin or config change is needed to turn them on. The generated footnotes section opens with a hidden-by-convention heading `<h2 class="sr-only" id="footnote-label">Footnotes</h2>`, but no `.sr-only` rule exists in the stylesheet, so the heading is visible to sighted readers — and the heading-autolink pass appends a `#` anchor link inside it, so a stray "Footnotes#" line appears above the list. The table-of-contents component lists every depth-2/3 heading in the post, so any post with footnotes gets a bogus "Footnotes" entry. The footnotes section itself has no styling.

Verified against the built output of the Go sync.Pool slices post: the TOC literally contains a "Footnotes" entry; footnote markup uses `user-content-fn-*` / `user-content-fnref-*` ids, `data-footnote-ref` refs, and `data-footnote-backref` links with `↩` text.

**Desired behavior:**
1. A general-purpose `.sr-only` visually-hidden utility (standard clip pattern) is defined in the global stylesheet and hides the footnote heading from sighted readers while keeping it announced to screen readers. The `#` autolink inside the heading is hidden with it; the residual screen-reader "#" noise is accepted — no pipeline change.
2. The table of contents excludes the footnote heading by filtering on the heading slug `footnote-label` (the generator's stable id), alongside its existing depth filter and trailing-`#` text stripping. Posts without footnotes are unchanged.
3. The `.footnotes` section is styled with blog-consistent tokens: `border-top: 1px solid var(--color-border)`, `font-size: 0.875em`, `color: var(--color-muted)`; links and backrefs use `--color-link` / `--color-link-hover` so dark mode works via the existing CSS variables. Backrefs (`↩`) read as a clear clickable affordance. Spacing follows the surrounding prose rhythm.

**Key interfaces:**
- `.sr-only` utility class: new, general-purpose, in the global stylesheet (not footnote-specific).
- `TableOfContents` component (receives `headings` of `{ depth, slug, text }`): filter out `slug === 'footnote-label'`.
- `.footnotes` CSS: style the section, its list items, and the `[data-footnote-backref]` links.

**Acceptance criteria:**
- [x] `sr-only` is defined and the "Footnotes" heading is not visible to sighted readers (still announced to screen readers)
- [x] The autolink `#` anchor is not visible on the footnote heading
- [x] A post with footnotes produces no "Footnotes" entry in the table of contents; posts without footnotes are unchanged
- [x] `.footnotes` has a top separator, muted/smaller type, working `↩` backrefs, and dark-mode colors via CSS variables
- [x] A built-HTML test asserts footnote ref/backref round-trip (ref `href` → definition `id`, backref `href` → ref `id`) on the existing Go sync.Pool slices post
- [x] Verified in a built post with multiple footnotes and a named footnote (`[^note]`), including one inside a paragraph followed by a list — via a throwaway probe post built and inspected during implementation, then removed

**Out of scope:**
- Excluding footnote text from `search-index.json` and `feed.xml` (raise separately if wanted)
- Cleaning up or editing the Go sync.Pool slices post's content (it is in-flight maintainer prose; use it only as a test fixture)
